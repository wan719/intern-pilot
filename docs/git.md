# Git 协作与提交约定

## 分支与同步

仓库 CI 在推送到 `main`、`dev` 及面向这两个分支的 PR 时运行。具体分支保护以远端设置为准；功能或修复建议使用独立分支与 PR，并在合并前查看 CI 结果。不要直接把当前工作区中不属于本次任务的改动加入提交。

```bash
git status --short
git fetch origin
git switch -c codex/<简短主题>
# 修改、验证后
git diff --check
git add <本次修改的文件>
git commit -m "docs: 补充项目开发约定"
```

同步远端前检查分支与未提交内容；遇到冲突逐文件解决并重新验证。不要用强制推送覆盖他人提交，也不要将 `.env`、令牌、生产数据、构建产物或个人运维记录提交到仓库。提交信息建议使用 `feat`、`fix`、`docs`、`test`、`refactor`、`chore` 等类型及清晰的中文或英文描述；每个提交聚焦一项可审查的改动。

## 合并与发布

PR 说明写清改动范围、实际验证命令及结果、数据或部署影响。发布标签对应实际发布的提交，不能把文档更新或本地构建等同于生产部署。[README 部署说明](../README.md#部署说明)仅是首次安装示例；数据库迁移、镜像更新、健康检查和回滚要核对目标环境并制定单独步骤。

## 从开始到 PR 的操作顺序

1. `git status --short` 和 `git branch --show-current`：确认当前分支及已有改动。若工作区已有未完成工作，先辨认归属，不用 `reset --hard` 或强制切换覆盖。
2. `git fetch origin`：了解远端新提交。基于目标分支创建任务分支；如果已有任务分支，继续使用它，不重复创建。
3. 修改和验证后检查 `git diff`、`git diff --check` 与 `git status --short`。只暂存本次文件，可用 `git add <路径>`；提交前用 `git diff --cached` 复核。
4. 推送任务分支并创建 PR 时，写清背景、修改点、实际测试结果、未测范围和迁移/部署影响。合并方式遵循仓库当时的保护规则，不绕过失败的 CI。

提交信息建议采用 `<type>: <说明>`。例如 `feat: 增加投递状态筛选`、`fix: 修复无权限页面跳转`、`test: 覆盖投递重复提交`、`docs: 更新本地启动说明`。不要仅写“update”或把互不相关的改动合成一次提交。

## 冲突与失败处理

同步或合并前先保护未提交工作。发生冲突时查看双方改动与业务含义，解决冲突标记后运行相关测试，再完成 rebase/merge；需要放弃当前 rebase 时使用 `git rebase --abort`。若远端分支已更新，先获取并整合新提交，不以 `--force` 覆盖他人工作。历史发布标签不可随意移动或重用。

## CI 与发布边界

[主 CI](../.github/workflows/ci.yml) 在 `main`、`dev` 的 push 与 PR 上运行后端测试及前端测试/构建。[Docker 构建工作流](../.github/workflows/docker-build.yml) 只针对 `main` 的 push 与 PR，验证 Compose 镜像可以构建。CI 通过不能证明数据库迁移、真实 AI/邮件服务或生产部署已完成。发布前还要核对目标提交、配置、备份与回滚；[README 部署说明](../README.md#部署说明)不替代环境专属发布方案。
