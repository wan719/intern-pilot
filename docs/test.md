# 软件测试规范

## 原则与范围

按变更风险选择测试，优先验证外部可观察行为、边界与失败路径。修复可复现缺陷时，尽可能增加能防止复发的回归测试；文档、格式等低风险改动以针对性核对为主。测试不得依赖或修改生产数据，不能通过删除测试、弱化断言或伪造结果来满足门禁。未执行的检查不得称为通过。

## 项目现有测试

| 范围 | 位置与工具 | 常用命令 |
| --- | --- | --- |
| 后端 | `backend/src/test/`；JUnit 5、Mockito、Spring Boot Test、MockMvc、H2、JaCoCo | `./gradlew test --no-daemon --max-workers=1` |
| 前端 | `frontend/src/**/__tests__/`；Vitest、Vue Test Utils | `npm run test:run` |
| 前端类型与构建 | `vue-tsc`、Vite | `npm run build` |
| CI | `.github/workflows/ci.yml` | 后端 `clean test jacocoTestReport`；前端 `npm ci`、`test:run`、`build` |

Windows 后端命令使用 `.\gradlew.bat`。从各自工程目录执行命令；前端先运行 `npm ci`。后端单个测试类可用 `./gradlew test --tests <完整类名>`。覆盖率报告位于 `backend/build/reports/jacoco/test/html/`；覆盖率帮助发现盲区，不替代行为断言。

## 按变更选择验证

- 业务服务、算法或缺陷修复：运行相关单元或服务测试，检查正常、边界、异常路径。
- Controller、鉴权或 RBAC：增加或运行接口与权限测试，核对 401/403、数据隔离和响应契约。
- SQL、事务或持久化：使用隔离测试库验证结构与数据行为；生产迁移还需单独评估备份、恢复和回滚。
- Vue 页面、路由、状态或请求封装：运行相关 Vitest 测试、类型检查及构建；重要交互再做手工浏览器核验。
- 配置或依赖升级：运行受影响模块的测试与构建，并检查 CI；生产部署变更需独立核验目标环境，[README 部署说明](../README.md#部署说明)只提供首次安装示例。
- 纯文档改动：检查命令、路径、链接与 `git diff --check`，无需为文档本身运行全套应用测试。

结束时简要报告变更内容、执行的命令及结果、未执行项和仍存在的风险。CI 结果、历史 README 记录与本次本地执行结果应明确区分。

## 测试层次和选择

| 层次 | 重点 | 项目中的做法 |
| --- | --- | --- |
| 单元/服务 | 业务分支、边界、错误处理 | JUnit 5 + Mockito；对纯计算逻辑、Service 与 AI 结果解析作直接断言 |
| 接口与权限 | 参数、响应、认证和授权 | MockMvc、Spring Security Test；覆盖 401/403 和资源所属关系 |
| 数据集成 | SQL、Mapper、事务与约束 | 使用隔离数据库或 H2 测试资源；对 MySQL 专有行为另作兼容性检查 |
| 前端组件 | 页面状态、交互和 API 调用 | Vitest + Vue Test Utils；对成功、失败、空数据及权限状态作断言 |
| 构建与人工验收 | 类型、打包、跨端交互及外部服务 | `npm run build`、必要的浏览器检查；真实 AI/邮件和生产状态分别验证 |

优先运行变更直接相关的测试；若改动共享鉴权、请求封装、数据库约束、路由或构建配置，再扩大到对应模块或完整 CI 命令。仅让覆盖率数字增加的测试没有价值，断言应针对用户或调用方可观察结果。

## 可执行命令

在 `backend/` 运行：

```powershell
.\gradlew.bat test --no-daemon --max-workers=1
.\gradlew.bat test --tests 'com.internpilot.util.VectorUtilsTest' --no-daemon
.\gradlew.bat clean test jacocoTestReport --no-daemon
```

在 `frontend/` 运行：

```powershell
npm ci
npm run test:run
npm run type-check
npm run build
```

Linux/macOS 后端命令使用 `./gradlew`。Gradle `test` 已配置在完成后生成 JaCoCo 报告；HTML 与 XML 位于 `build/reports/jacoco/test/`。前端 `build` 已包含类型检查，单独执行 `type-check` 便于定位类型问题。CI 的确切命令及触发条件以 [工作流文件](../.github/workflows/ci.yml) 为准。

## 失败处理与报告

测试失败时保留命令、退出码、报错和复现条件，先分清产品缺陷、测试断言问题与环境依赖问题。修复根因后重跑失败测试及受影响回归范围；不能删除测试、跳过断言或把环境错误写成通过。若测试需要数据库、Redis 或外部服务，应说明所用隔离环境和未覆盖的真实服务行为。

交付报告至少写明：变更文件或功能、运行目录与命令、通过/失败/跳过数量或退出结果、手工检查范围、未执行项及原因、剩余风险。文档改动可报告路径和链接核对结果；生产验收必须有独立的目标环境证据。

## 提交与合并门禁

| 阶段 | 最低检查 | 不能据此声称 |
| --- | --- | --- |
| 开发中 | 运行直接相关的快速测试；修复失败后重跑 | 全仓库无回归 |
| 提交前 | 查看改动、运行相关测试和 `git diff --check` | CI 与部署已通过 |
| PR | 查看后端测试、前端 Vitest/构建及适用的 Docker 构建检查 | 真实 AI、邮件、生产数据库已验收 |
| 部署前 | 核对目标提交、配置、备份、迁移、回滚和核心业务流程 | 健康接口单独等于业务验收 |

没有项目统一的强制覆盖率百分比。JaCoCo 报告用于找出核心业务、条件分支和新风险代码的测试盲区。若测试失败或被跳过，须说明影响并修复或记录接受原因，不能把门禁表述为通过。

## 典型回归范围

- 认证、用户资料或 RBAC：登录/过期 token、普通用户和管理员权限、跨用户资源访问、前端路由守卫。
- 简历上传或版本：文件类型与大小、解析失败、默认版本、文件与数据库记录一致性。
- 岗位、推荐或投递：创建与更新、重复记录、软删除、分页筛选及状态流转。
- AI 分析、面试题或 RAG：Mock 下的结果解析、失败与重试、缓存键、异步任务进度和刷新恢复；真实外部服务另行检查。
- 页面布局与导航：桌面和移动端入口、加载/空/失败状态、管理员菜单、打印页。

这些是选择检查范围的起点，不表示每项已有自动化覆盖。实际测试类和命令应从当前仓库确认；新增缺陷回归测试要能在修复前失败、修复后通过，并且验证行为而非仅复述实现。
